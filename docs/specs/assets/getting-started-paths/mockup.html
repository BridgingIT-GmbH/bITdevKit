Add DevKit to an existing app

This page starts with a plain minimal API called Parcels and makes it a DevKit host in ten steps. The first four change only Program.cs. Steps 5 and 6 move the routes into an endpoints class and the logic into command and query handlers. Step 7 groups the feature into a module. Steps 8 and 9 hand the DbContext to DevKit and put a repository in front of it. Step 10 gives Parcel a factory that records a domain event, and the repository publishes it after the save. The app builds and runs after each step.

Hand the basics to an agent

An agent that can edit files and run dotnet commands can apply the ten steps to your app, with your names in place of the sample's. It plans first and waits for your approval, then commits each step on its own so you can review it.

Before you start, you need:

  • a branch from a clean working tree
  • a local development database, because step 8 applies migrations at startup
  • an agent with file and shell access, such as GitHub Copilot in agent mode, Claude Code or Codex

Group the feature into a module

AddsModules Packagesnone new TouchesProgram.cs Time~5 min

Program.cs still registers the DbContext and the endpoints for Parcels. A module takes over those two lines, and the host adds the whole feature area with one call. The next feature area gets its own module and one more WithModule line.

Program.cs
using BridgingIT.DevKit.Common;using BridgingIT.DevKit.Presentation.Web;using Parcels.Web.Parcels;var builder = DevKitWebApplication.CreateBuilder(args)    .AddLogging();builder.Services.AddModules(builder.Configuration, builder.Environment, m => m    .WithModule<ParcelsModule>());builder.Services.AddRequester()    .AddHandlers()    .WithBehavior(typeof(ValidationPipelineBehavior<,>));var app = builder.Build();app.UseRequestCorrelation();app.UseRequestModuleContext();app.UseRequestLogging();app.UseModules();app.MapModules();app.MapEndpoints();app.Run();
Parcels/ParcelsModule.cs
namespace Parcels.Web.Parcels;using BridgingIT.DevKit.Common;using Microsoft.EntityFrameworkCore;public class ParcelsModule : WebModuleBase{    public override IServiceCollection Register(        IServiceCollection services,        IConfiguration? configuration = null,        IWebHostEnvironment? environment = null)    {        services.AddDbContext<ParcelsDbContext>(options =>            options.UseSqlite(configuration?.GetConnectionString("Parcels")));        services.AddEndpoints<ParcelEndpoints>();        return services;    }    public override IApplicationBuilder Use(        IApplicationBuilder app,        IConfiguration? configuration = null,        IWebHostEnvironment? environment = null)    {        return app;    }    public override IEndpointRouteBuilder Map(        IEndpointRouteBuilder app,        IConfiguration? configuration = null,        IWebHostEnvironment? environment = null)    {        return app;    }}

AddModules calls Register while the host builds. UseModules() and MapModules() call Use and Map. Both return app here, because the routes already live in ParcelEndpoints. The module takes its name from the class, so it is parcels.

Overview

Queueing provides an application-level abstraction for background work that must be processed by exactly one logical handler per queued message type. It complements Messaging rather than replacing it.

Queueing or Jobs

Queueing dispatches work items to a logical consumer. Jobs manages job definitions, triggers, occurrences, and execution attempts. Both can run background work.

Choose Queueing when

  • a producer sends a work item that one registered handler owns
  • producers and consumers communicate through a queue contract
  • a queue transport or competing workers fit the deployment
  • waiting work, subscriptions, and queue controls are the main operational concerns

IQueueBroker enqueues messages for IQueueMessageHandler<TMessage> implementations. Each queued message type has one logical handler registration, even when several workers compete for work.

Choose Jobs when

  • work runs on a recurring schedule, calendar, delay, or manual trigger
  • operators need to inspect occurrences, attempts, and execution history
  • job-level concurrency, chaining, batches, or interruption matter
  • accepted events should create scheduler-managed work

IJobSchedulerService dispatches registered jobs. A manual job can fit even without a recurring schedule when execution history and scheduler controls matter.

agent-support-guide.md

Prompt library

State what the agent must inspect first, what it can change, and when it must wait for approval. Runtime prompts require the application and bdk mcp to be running. Documentation, API reference, and guidance prompts work without a running application.

Runtime orientation

Use the bdk MCP tools to verify the selected runtime. Run the MCP self-test, inspect the available capabilities, and summarize which diagnostics are available before changing code.
Use bdk MCP to check whether this application exposes logs, operation and request profiling, Blob Storage diagnostics, jobs, messaging, queueing, orchestrations, and project-owned operations. Tell me which areas are available and which are not.

Work in a Git worktree

Start the application of this worktree with bdk dev run. Use bdk_runtimes_current to get its URL, and confirm the selected runtime belongs to this worktree before testing in the browser.

Debug a local feature

Use bdk MCP to inspect the latest errors from the running app. For the newest error, use bdk_investigate_correlation to inspect related logs and operation recordings. Summarize the evidence and point me to the most likely code area.
I just reproduced a bug locally. Use bdk MCP to tail recent warning and error logs from the last 10 minutes, then suggest the smallest code change to investigate first.
