# Design Specification: Storage Permalinks

> Provide stable, opaque, registry-backed download links for Blob Storage, Document Storage, and File Storage resources.

[TOC]

## Overview

Storage Permalinks provide stable download URLs for resources managed by the devkit storage features.

The feature is shared by Blob Storage, Document Storage, and File Storage. It does not make individual storage providers responsible for public download links. Instead, a separate permalink registry owns a stable identifier and maps that identifier to the current storage resource location.

The registry is the source of truth for permalink resolution. The stored blob, document, or file is not the source of truth for the permalink identifier.

Permalinks are useful when a resource must be downloadable through a stable URL while the resource may be renamed or moved inside the same configured storage registration. The public identifier is opaque, cryptographically random, and does not reveal storage kind, registration name, provider name, container, partition key, document key, blob key, or file path.

Storage Permalinks support these registry providers:

* In-memory registry provider.
* Entity Framework Core registry provider.

Storage resources opt into permalink tracking through storage-specific behavior additions. Storage providers remain focused on storage operations.

## Goals

The goals of this feature are:

* Provide a shared permalink feature for Blob Storage, Document Storage, and File Storage.
* Keep permalink identifiers stable across supported same-registration resource moves.
* Use the permalink registry as the source of truth for identifier-to-location mapping.
* Keep storage providers unaware of permalink identifiers.
* Require explicit opt-in per storage registration.
* Provide in-memory and Entity Framework Core registry providers.
* Support stable anonymous download URLs when configured.
* Support optional authorization for permalink downloads through endpoint options.
* Support expiration on permalink identifiers.
* Support replacing and clearing permalink expiration without changing the identifier.
* Support deleting a permalink without deleting the underlying resource.
* Support listing and maintenance operations for dashboards and operators.
* Support optional optimistic concurrency through ETags on maintenance operations.
* Preserve permalink identifiers during same-registration Blob, Document, and File Storage moves.
* Tombstone permalink mappings when opted-in storage clients delete resources.
* Tombstone permalink mappings when opted-in storage retention removes resources.
* Keep registry writes decoupled from storage writes.
* Use asynchronous change handling for storage-to-registry synchronization.
* Provide bounded queueing and retry behavior for synchronization.
* Avoid cross-provider and cross-registration move preservation.
* Return generic not-found download responses for invalid, expired, deleted, missing-target, or unavailable-target links.
* Use the correct content type for blob and file downloads.
* Return documents as JSON downloads.
* Expose compact dashboard actions on storage dashboards.
* Provide a separate permalink dashboard for list, download, copy, expiration, and delete operations.
* Emit low-cardinality metrics for registry operations, synchronization, and downloads.

## Non-Goals

This feature does not introduce:

* Provider-native public access URLs.
* Presigned URLs generated by individual storage providers.
* Storing permalink identifiers as the authoritative state on each resource.
* Renewal or rotation of an existing permalink identifier.
* Cross-registration move preservation.
* Cross-provider move preservation.
* Distributed transactions between storage providers and the permalink registry.
* Exactly-once registry synchronization.
* Periodic full scans of storage providers to discover external changes.
* Observing direct provider, database, filesystem, or Azure changes made outside devkit storage clients.
* User-facing directory sharing semantics beyond tracked file paths.
* Authorization decisions inside storage providers.
* Encrypting registry locations by default.
* Exposing storage locations when permalink resolution fails.

## Terminology

| Term | Meaning |
| --- | --- |
| Permalink | Stable public download link backed by a registry entry. |
| Permalink ID | Opaque random identifier used in the public URL. |
| Registry | Provider-neutral service that stores permalink entries. |
| Registry provider | Concrete persistence implementation for registry entries. |
| Storage kind | Resource family: blob, document, or file. |
| Registration name | Configured storage client or provider name. |
| Resource location | Provider-neutral address of the storage resource within a registration. |
| Active entry | Registry entry that can resolve to a resource if not expired. |
| Tombstone | Registry entry state that prevents a deleted location from resolving. |
| Expiration | Optional timestamp after which the permalink no longer resolves. |
| Maintenance service | Privileged API for listing, inspecting, updating, and deleting registry entries. |

## Public API Shape

The feature belongs in `Application.Storage/Permalinks`.

The main abstractions are:

* `IStoragePermalinkRegistry`
* `IStoragePermalinkRegistryProvider`
* `IStoragePermalinkMaintenanceService`
* `StoragePermalinkEntry`
* `StoragePermalinkId`
* `StorageResourceLocation`
* `StoragePermalinkCreateOptions`
* `StoragePermalinkListOptions`
* `StoragePermalinkExpirationUpdate`
* `StoragePermalinkDeleteOptions`
* `StoragePermalinkRegistrationBuilder`

Storage-specific opt-in methods attach permalink behavior to configured registrations:

```csharp
services.AddBlobStorage()
    .WithInMemoryClient("reports")
    .WithPermalinks("reports");

services.AddDocumentStorage()
    .WithInMemoryClient<Report>(name: "default")
    .WithPermalinks<Report>("default");

services.AddFileStorage(factory => factory
    .RegisterProvider("files", builder => builder
        .UseInMemory("files")
        .WithPermalinks()));
```

Registry provider selection is explicit:

```csharp
services.AddStoragePermalinks()
    .UseInMemory()
    .AddDownloadEndpoints();
```

For durable registry state, an application `DbContext` implements the registry context contract and exposes the registry `DbSet`:

```csharp
services.AddStoragePermalinks()
    .UseEntityFramework<AppDbContext>()
    .AddDownloadEndpoints();
```

## Registry Model

Each registry entry stores:

* Stable permalink identifier.
* Storage kind.
* Storage registration name.
* Provider-neutral resource location.
* Active or deleted state.
* Optional expiration timestamp.
* Created timestamp.
* Updated timestamp.
* Deleted timestamp when tombstoned.
* Provider-neutral ETag or version for maintenance concurrency.

The permalink identifier is generated by the registry. It is a random 256-bit value encoded as Base64Url.

Repeated permalink creation for the same active location returns the existing active identifier. Deleting a permalink revokes that identifier. A later real write to the same resource location may create a new identifier.

Permalink identifiers are immutable. They cannot be renewed or rotated in place. Expiration can be replaced or cleared on the same identifier.

## Consistency Model

Storage writes and registry writes are intentionally not part of one transaction.

Opted-in storage clients publish bounded in-process change notifications after successful devkit storage operations. A hosted dispatcher consumes those notifications in fresh dependency-injection scopes and updates the registry. Failed synchronization is retried according to configured retry options.

The synchronization rules are:

* Uploads, upserts, and saves ensure an active mapping exists for the current location.
* Deletes tombstone the mapping for the deleted location.
* Delayed older upsert notifications cannot recreate a location after a newer tombstone.
* Same-registration moves preserve the existing permalink identifier and expiration.
* Copy followed by failed source delete keeps or creates the target mapping and does not move the source mapping.
* Cross-registration moves do not preserve permalink identifiers.
* File directory moves update tracked descendant locations.
* File recursive deletes tombstone tracked descendant locations.
* Blob and Document retention operations tombstone exactly the resources that were physically removed by the provider.

There is no periodic provider scan. Changes made outside devkit storage clients are not observed. A later verified `GetPermalinkAsync` call may repair a missing active mapping if the target resource exists.

## Download Endpoint

The default download route is:

```text
GET /_bdk/api/storage/permalinks/{id}
```

The route resolves the registry entry, verifies that it is active and not expired, resolves the configured storage client, confirms the target exists, and streams or serializes the resource.

Download behavior:

* Blob downloads use the blob content type.
* File downloads use the stored or inferred content type.
* Document downloads return JSON.
* Responses include `Cache-Control: private, no-store`.
* Responses include `Referrer-Policy: no-referrer`.
* Invalid identifiers return not found.
* Expired identifiers return not found.
* Deleted identifiers return not found.
* Missing physical targets return not found.
* Unavailable target registrations return not found.

The endpoint is anonymous by default because the random identifier is the bearer credential. Applications can require authorization through endpoint options:

```csharp
services.AddStoragePermalinks()
    .UseInMemory()
    .AddDownloadEndpoints(options => options
        .RequireAuthorization()
        .RequirePolicy("StorageDownloads"));
```

## Expiration and Maintenance

Permalink expiration controls the link only. It does not delete or modify the underlying storage resource.

`IStoragePermalinkMaintenanceService` supports:

* Bounded listing.
* Lookup including expired and deleted entries.
* Replacing expiration.
* Clearing expiration.
* Deleting a permalink.
* Optional ETag checks for updates and deletes.

Deleting a permalink revokes that identifier and does not delete the underlying resource.

## Dashboard

Storage dashboards surface compact permalink actions only for registrations that opted into permalink tracking.

Blob, Document, and File Storage dashboard tables expose:

* Direct download through permalink.
* Copy permalink URL.
* Permalink creation when needed.
* Current resource metadata already shown by the storage dashboard.

The separate Permalinks dashboard page exposes:

* Bounded list view.
* Filtering by storage kind and registration where supported.
* Download action.
* Copy link action.
* Expiration update.
* Expiration clearing.
* Delete action.

The dashboard is operational tooling, not the public permalink API. It must stay compact and consistent with the Blob and Document Storage dashboard style.

## Metrics

The feature emits metrics through the `BridgingIT.DevKit.Storage.Permalinks` meter.

Metrics cover:

* Registry operations.
* Download operations.
* Synchronization events.
* Synchronization retries.
* Queue depth.
* Operation durations.

Metric tags are low-cardinality. They may include operation, outcome, storage kind, and registry provider. They must not include permalink identifiers, keys, paths, containers, partitions, or document identifiers.

## Security

Permalink IDs are bearer credentials when anonymous downloads are enabled.

Security requirements:

* Use high-entropy random identifiers.
* Do not expose storage locations in failed download responses.
* Do not put permalink identifiers in metric tags.
* Prefer finite expiration for externally shared links.
* Allow applications to require authorization through endpoint options.
* Preserve normal storage authorization for dashboard and maintenance endpoints.
* Do not treat storage keys and paths as encrypted secret material by default.

## Provider Requirements

### In-Memory Registry Provider

The in-memory provider is process-local and volatile.

It is suitable for:

* Unit tests.
* Development.
* Single-process demos.
* Non-durable scenarios.

It is not suitable for persistent public links.

### Entity Framework Core Registry Provider

The EF Core provider is the durable registry provider.

Requirements:

* The provider owns its operation scopes.
* The application context implements the registry context contract.
* Registry entity configuration is declared on the entity through annotations where possible.
* ETags or versions are maintained for maintenance concurrency.
* Queries support bounded listing.
* Deleted entries remain tombstoned.

## Acceptance Criteria

1. Given a Blob, Document, or File Storage registration has opted into permalinks, when a permalink is requested for an existing resource, then a stable opaque identifier is returned.
2. Given a permalink exists for a resource, when the resource is moved inside the same registration, then the existing identifier resolves to the new location.
3. Given a permalink exists for a resource, when the resource is deleted through an opted-in storage client, then the identifier no longer resolves.
4. Given a permalink has expired, when the download endpoint is called, then the endpoint returns not found without exposing the target location.
5. Given a permalink target registration is unavailable, when the download endpoint is called, then the endpoint returns not found instead of leaking internal provider details.
6. Given a blob is downloaded through a permalink, when the response is produced, then the blob content type is used.
7. Given a permalink is deleted through the maintenance service, when the underlying resource still exists, then only the permalink is revoked.
8. Given a dashboard user opens a storage dashboard for an opted-in registration, then compact permalink download and copy actions are available.
9. Given an operator opens the Permalinks dashboard, then existing entries can be listed, downloaded, copied, expired, cleared, or deleted.
10. Given permalink operations run, when metrics are emitted, then no identifiers, keys, paths, containers, partitions, or document IDs are used as metric tags.
