# Introduction

![Status: Completed](https://img.shields.io/badge/status-Completed-brightgreen)

Implement the finalized Auditing specification: Common scope contracts, a bounded Application recorder, memory and three-backend EF storage, explicitly selected feature contributors, protected/searchable evidence, export and operational UI, diagnostics, test helpers, and runnable fictional adoption. The first phase proves storage publication/lifecycle feasibility before production persistence and extraction depend on it. Implementation began and completed on 2026-10-30. The user has authorized a validated local commit after each implementation phase. The user approved a fourth physical table for singleton technical control state on 2026-10-30. The storage tests use that explicit schema decision.

The source specification is [Auditing](../docs/specs/spec-application-auditing.md), version 1.1, status implemented. This plan embeds all 52 requirements and maps each to task IDs. Its interpretation does not require prior conversation. Existing NDJSON source anchors at this baseline include `src/Common.Serialization/Ndjson/NdjsonWriter.cs:34`, `src/Common.Serialization/Ndjson/NdjsonReader.cs:70`, `src/Presentation.Web/Ndjson/NdjsonHttpResult.cs:24`, and the public contracts in `NdjsonStreamOutcome.cs`/`INdjsonStreamObserver.cs`. Paths/symbols remain authoritative if unrelated line numbers move.

The approved schema has three audit data tables plus `__Auditing_StoreState`, a singleton technical control table. See [ADR-0031](../docs/adr/0031-audit-store-publication-and-control-state.md). Native backup/restore conformance covers SQL Server, PostgreSQL and SQLite; phase 1 proves durable reopen, control-state retention, and explicit epoch-rotation semantics.

## 3. Alternatives

- **ALT-001**: Persisting mutable start/update audit rows was rejected. The accepted lifecycle publishes one immutable record after root completion; diagnostics exposes capacity/delivery facts, not in-progress business records.
- **ALT-002**: Implicit feature opt-ins or a second integration list on AddAuditing were rejected. Source-builder selection is local, explicit, order-independent and idempotent.
- **ALT-003**: Making auditing depend on repositories/Active Entities/ChangeHistory was rejected. They are optional contributors; the EF provider uses audit DbSets directly and source history remains responsible for actual diffs.
- **ALT-004**: Using identity allocation/event time/search-page numbers as an extraction cursor was rejected. Only a proved committed-prefix position with epoch/lifecycle/availability validation can issue a completed-window checkpoint.
- **ALT-005**: A fourth table, synthetic audit root or another feature's coordination state is not selected to bypass the compact-schema gate. If no conforming design passes TASK-004, execution stops On Hold before dependent code.
- **ALT-006**: A separate Application queue in front of EF, silent eviction of accepted writes, automatic inline fallback, and memory fallback after EF failure were rejected. One bounded provider queue has explicit receipts and crash-loss limits.
- **ALT-007**: Automatic whole-parameter/result/file/row capture was rejected. Safe business context is explicitly projected and centrally constrained; source evidence policies cannot be relaxed by auditing.
- **ALT-008**: Plain hashes were rejected as an authenticity claim. Optional host-key HMAC verifies original content; digital signatures, deletion detection, immutable external storage, and SIEM forwarding are separate capabilities.
- **ALT-009**: Reimplementing NDJSON or wrapping audit entries in the general streaming envelope was rejected. Reuse delivered raw exact-byte/observer contracts while keeping Auditing's own completion and checkpoint semantics.
- **ALT-010**: Browser fetch-to-Blob/full-result buffering was rejected for dashboard downloads. Native bounded form submission streams an attachment and uses companion metadata for progress/continuation.
- **ALT-011**: A mandatory Auditing permission service/policy was rejected. Existing host access remains; optional trusted read-scope composition supplies row constraints and fails closed once selected.
- **ALT-012**: Shipping SQL Server first and leaving SQLite/PostgreSQL semantics weaker was rejected by the user's confirmed first-release scope. All three backends must pass conformance.

## 7. Risks & Assumptions

- **RISK-001**: Durable store identity, epochs and publication ordering must remain correct across empty stores, restarts and restores. Keep the three-backend storage tests and the approved singleton control-table design.
- **RISK-002**: Backend JSON, Unicode, collation, transaction and locking semantics differ. Shared logical vectors and real backend tests prevent a silently weaker provider; no post-page in-memory filtering substitutes for translation.
- **RISK-003**: Capture finalization can perform asynchronous key resolution and admission. Async root ownership and fresh bounded finalization budgets are required even after client cancellation; source failures and started responses cannot be replaced by audit errors.
- **RISK-004**: The accepted EF queue can lose admitted records on abrupt termination, and memory/retention can remove evidence. Capabilities, receipts, diagnostics and documentation must disclose those limits. No stronger durable-handoff or business/audit atomicity promise is added.
- **RISK-005**: Source ChangeHistory commit outcomes and worker attribution can be unobservable/untrusted. Preserve Unknown/no-value evidence and unavailable links rather than infer commits, actors, recipient delivery or job execution.
- **RISK-006**: Exact export budgets/digests and failed final writes can disagree with source enumeration completion. Use original frames plus terminal output/cleanup accounting; client confirmation remains separate. Metadata publication and instance loss can remain unavailable.
- **RISK-007**: HMAC keys retained too briefly, unsupported old canonical profiles, or lossy EF reconstruction break historical verification. Golden vectors, lossless JSON fragments, key rotation and restore tests are release gates; never silently re-sign or relabel history.
- **RISK-008**: The implementation spans many packages and shared behavior builders. Explicit dependencies, source-local metadata, code review, isolated test providers and focused tests limit accidental opt-ins or boundary leakage.
- **RISK-009**: Public read scope defaults to unrestricted store data under host access. Tenant-isolated deployments must opt into trusted restrictions and capture an approved tenant key; an actor ID or client filter is not row authorization.
- **RISK-010**: Earlier terminal queue failures intentionally make subsequent cumulative flushes report historical loss. Preserve bounded failure aggregates and expose receipt-scoped observations; never reset the epoch silently to make a check green.
- **ASSUMPTION-001**: The confirmed first-release backend list, three-data-table mapping, ReportOnly/buffered defaults and complete feature scope remain authoritative throughout execution.
- **ASSUMPTION-002**: .NET 10, existing CPM package versions and local/CI test containers remain available; unavailable prerequisites block their validation instead of narrowing scope.
- **ASSUMPTION-003**: The library implementation owns local source/tests/docs and phase commits. Production key provisioning, tenant policy, operating procedures, clocks, deployment permissions, backup custody and any compliance assessment remain explicit host responsibilities.
- **ASSUMPTION-004**: Application-specific proof is produced with fictional test data and stored outside docs. The public guide/ADRs/specs remain self-contained and do not reference repository example applications.
- **ASSUMPTION-005**: All phase checkpoints are local commits only. Inspect and preserve any concurrent user changes; no branch rewrite, remote push, tag, PR, release or deployment is authorized by this plan.
