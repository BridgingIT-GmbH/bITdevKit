# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

Implement the universal backend cache defined in [the Application Caching specification](../docs/specs/spec-application-caching.md). Deliver collections, typed and binary access, shared loading, bounded storage, three providers, optional hot entries, independent background services, and optional web management. This plan covers the full feature. Phases describe implementation dependencies, not separate releases.

The baseline is the specification reviewed on 2026-11-04, including decisions D-01 through D-33 and acceptance stories 15.1 through 15.58. Runtime implementation has not started. All implementation tasks remain unchecked. Paths beginning with `src/`, `tests/`, `benchmarks/`, `docs/`, or `plan/` are relative to the repository root. Within a task, shorter file paths are relative to the first fully specified file's directory. New paths and symbols below are implementation targets; reference paths in section 8 already exist. Symbol references, rather than line numbers, identify existing code because implementation will move lines.

## 1. Requirements & Constraints

- **REQ-001**: Add `Application.Caching` as a separate advanced feature. Preserve `Common.Caching`, `ICacheProvider`, `AddCaching()`, and their existing consumers and registrations.
- **REQ-002**: Declare an immutable startup collection catalog. Each collection has one registered value-contract alias and one named complete provider. Identity is namespace, collection, contract version, and key. All keys, dimension names, and string dimension values always compare with ordinal-ignore-case semantics across providers.
- **REQ-003**: Provide typed `ICacheCollection<T>` and binary `ICacheBinaryCollection` handles through `IApplicationCache`. Distinguish hit, miss, loaded/joined/bypassed, successful null/empty values, confirmed source absence, and actual storage outcomes using DevKit `Result` contracts.
- **REQ-004**: Implement direct access, ordered partial batches, node-local shared loading by default, optional capable-provider shared-store coordination, explicit independent loading, bypass, and conditional refresh. One owner executes source work; followers receive completion without repeating that work or sharing a consumed stream/`ValueTask`.
- **REQ-005**: Fence active publication on exact removal, filter invalidation, and explicit clear, including absent keys and late dimensions. Logical collection invalidation covers retained contract versions in the selected store. Expose partial effects and cross-provider child outcomes without claiming a distributed transaction.
- **REQ-006**: Implement one bounded typed selection model for all providers: exact key, literal prefix, escaped whole-key glob, scalar equality, set membership, half-open interval overlap, presence/absence, publication-time ranges, stored-size ranges, and explicit AND/OR. Empty selection matches nothing. Clear is a separate operation.
- **REQ-007**: Separate logical expiration from physical retention and eviction. Enforce finite absolute TTL by default, optional authoritative sliding expiry with a hard age cap, stable acquired read versions, hierarchical reservations, and bounded cleanup. New callers never receive expired or invalidated data.
- **REQ-008**: Add cache-independent `IValueCodec<T>`, capability descriptors, registered resolution, and optional `IValueCodecValidator<T>` to `Common.Serialization`. Supply forward-only BCL System.Text.Json access and compatible serializer adapters. Preserve `ISerializer` registrations and public behavior.
- **REQ-009**: Persist binary payloads and explicit versioned envelopes with integrity and sizes. Support optional GZip/Brotli transformation with explicit algorithm/level, threshold/minimum saving, single encoding, bounded same-store staging, and safe intact-original fallback. Unknown payload formats are controlled compatibility misses; incompatible provider metadata fails readiness.
- **REQ-010**: Supply in-memory, Entity Framework, and filesystem providers. A provider owns payloads, indexes, versions, fences, readers, quota, coordination, and recovery in its selected store. SQL Server, PostgreSQL, and SQLite are EF profiles. Local disks, SMB, and NFS are filesystem profiles.
- **REQ-011**: Implement EF-owned schema/context and engine-specific migration artifacts, indexed small reads, metadata-only validation/querying, bounded chunk storage, atomic publication, shared reservations, and recovery. Hosts deploy schema changes and signal database readiness; requests/workers never apply DDL.
- **REQ-012**: Implement the native filesystem version-one journal/index/manifest protocol in `Infrastructure.FileSystem`. Reuse filesystem operations, paths, authority, durability, and error classification directly. Support local multiprocess and qualified shared multihost access on Windows/Linux without directory scans as an index or timeout-based uncertain-owner takeover.
- **REQ-013**: Keep the collection-owned hot-entry layer disabled by default. Explicit opt-in supports Binary, Decoded, or BinaryAndDecoded where eligible. Every reuse establishes authoritative provider validity. Promotion, pins, decoded immutability/estimates, and local eviction remain bounded; provider failure never grants hot fallback.
- **REQ-014**: Expose three behavior stages: public collection operations, owned source execution, and binary payload transformation. Compose chains once with the first registration outermost. Keep identity, validity, fencing, limits, and ownership mandatory. Provide selectable logging, metrics/tracing, profiling, auditing integration, source resilience, and compression.
- **REQ-015**: Schedule refresh, warm-up, cleanup, and operation continuation with cache-owned `PeriodicBackgroundService` implementations. Follow application-start, startup delay, named `IDatabaseReadyService`, scope, nonoverlap, shutdown, and stuck-work accounting conventions. Refresh/warm-up default off and use trusted registered loaders.
- **REQ-016**: Combine fluent configuration and the host's `IConfiguration` using property presence. Precedence is built-in defaults, global fluent, collection fluent, configured global, configured collection. Explicit false/zero/empty values survive merging. Stage behavior lists replace lower-precedence lists. Freeze validated effective settings and their provenance at startup.
- **REQ-017**: Put HTTP, Dashboard, Console Commands, and MCP adapters in new `Presentation.Web.Caching`. Enable each independently. `WithEndpoints()` alone opts into the external API; collections are then exposed unless excluded in fluent/configuration. Authorized requests explicitly targeting an excluded collection fail with HTTP 400 before cache/provider or payload access.
- **REQ-018**: Use `EndpointsBase`, explicit binding, private methods, `IRequester.SendAsync`, FluentValidation, DTOs, shared Result/Problem Details mapping, cancellation, authorization, and OpenAPI metadata. HTTP get never activates a loader. Large transfers use owned streaming handles without whole-body buffering.
- **REQ-019**: Supply default `no-store`, optional private revalidation, opaque representation/version ETags, metadata-only conditional GET, and commit-checked `If-Match`/create-only conditions. Distinguish 200, 202, 206, 304, 400, 404, 412, and 416; post-start transfer errors abort rather than replace delivered content.
- **REQ-020**: Supply overview and collection Dashboard pages with routed tabs, including Diagnostics charts and Operations. Use existing RazorSlices, remembered views, path helpers, refresh/chart lifecycle, authorization, redaction, and finite metric histories. Charts distinguish real zeros from unavailable observations and process-local scope from shared-store scope.
- **REQ-021**: Add optional downward-only expiration jitter, explicit negative caching, and named-provider circuit breaking. They are disabled by default. Errors never become negative entries, circuit failures never become ordinary misses, and jitter never extends freshness.
- **REQ-022**: Add node-local pause/resume for configured background refresh/warm-up, plus tracked, cancellable, resumable filter invalidation and clear. Keep continuation/status in the selected provider. Persist fixed scope/cutoffs, conditional progress, and accurate outcomes; cancel stops remaining work without rolling back committed effects.
- **REQ-023**: Deliver benchmarks and numeric reports for all three providers, EF engines, and filesystem qualification profiles. Report operations/s, successful entries/s, allocations, latency percentiles, memory, source invocations, and provider I/O. Use the existing Common, Application, and Presentation benchmark projects.
- **SEC-001**: Obtain namespace/tenant authority from trusted host context. Dimensions alone are not authorization. Do not load CLR types or code from persisted/request/configuration strings. Redact keys, dimensions, credentials, and principals in diagnostics and operational history.
- **SEC-002**: Validate root-relative filesystem references, links, canonical identities, collision checks, sizes, decompression, metadata, and supported readers before publication/delivery. Apply read/write/invalidation policy selection consistently. Authorize every mutation and retain bounded reason/origin metadata.
- **CON-001**: Runtime projects target `net10.0`; resolve SDK/package versions from `global.json`, project files, and central package management. Use existing BCL/Microsoft packages and existing DevKit results, requester, metrics, profiling, resilience, and filesystem mechanisms. Do not add a direct Polly dependency.
- **CON-002**: Common depends on no cache feature. `Application.Caching` depends only on Common packages. Infrastructure implements Application contracts. `Presentation.Web.Caching` references Application and existing Presentation infrastructure. Add no caching dependency to Domain.
- **CON-003**: Add no Blob/DocumentStorage adapter, extra metadata database, hidden SQLite filesystem index, generic job framework, live configuration reload, automatic payload migration, stale-serving mode, recursive dependency graph, or dynamic request-created collection.
- **CON-004**: Use ordinary UTC and `TimeProvider`. Add no dedicated clock-skew protocol or machinery. Background scheduling has no Jobs or StartupTasks dependency.
- **CON-005**: Enforce finite cache-owned reservations, not a claimed hard limit on the whole managed heap, database log, or server disk. Keep native work accounted until it actually stops. A timeout alone cannot prove ownership transfer or free occupied resources.
- **CON-006**: Use normal existing tests and CI. Add shared test scenarios only inside existing test projects. Add no separate conformance service, generated acceptance manifest, browser verification project, or flaky wall-clock unit-test gates.
- **GUD-001**: Document public symbols with XML examples. Use fictional self-contained product/report examples in documentation. Keep generated benchmark raw artifacts in normal benchmark output and machine/application-specific execution evidence outside `docs/`.
- **PAT-001**: Reuse `DocumentStoreClientBehaviorBase<T>` forwarding and registration conventions without depending on Application.Storage. Reuse existing readiness/hosting and Dashboard page conventions. Source mutation commits before application-triggered invalidation; reliable delivery uses existing outbox/messaging where needed.

## 2. Implementation Steps

Execute only after a separate instruction authorizes implementation. Creating this plan does not execute the tasks. Update a task's Completed and Date cells only when its implementation and listed validation pass. Use `✅` and the actual completion date. All paths named below must be included in the corresponding change or explicitly retained when already correct.

Each phase declares entry dependencies and completion criteria. A task inherits its phase dependencies plus its own **Depends** list. Tasks may run independently only when these dependencies are complete and their files do not overlap. Serialize edits to shared project files. Run top-level builds and test commands sequentially in one worktree. Test identifiers refer to section 6; validate the task's implemented cases within those groups, which later phases extend. Each phase leaves the affected projects buildable and validates its completed capabilities; the full feature is complete only after Phase 16.

## 3. Alternatives

- **ALT-001**: Extending or replacing Common.Caching would change the minimal feature's contracts and consumers. Keep advanced registration, configuration, handles, and providers separate.
- **ALT-002**: Splitting metadata from payloads through another storage feature adds independent stores and consistency work. Each selected cache provider owns both in one store.
- **ALT-003**: A separately selected in-memory front provider would complicate authority and invalidation. Use optional engine-owned hot representations and strict selected-provider validation.
- **ALT-004**: Trusting local TTLs, notifications, or a validation interval would weaken acknowledged shared invalidation. Validate each hot reuse; use notifications only to retire candidates earlier.
- **ALT-005**: Jobs, StartupTasks, and a durable generic work queue add scheduling dependencies. Use existing Common background services and bounded cache-provider maintenance records.
- **ALT-006**: A hidden SQLite metadata backend or directory-wide filesystem catalog conflicts with the native provider design. Use the agreed bounded journal/index/manifest format; SQLite remains an EF profile.
- **ALT-007**: Universal latency promises or speed assertions in unit tests conceal device/network variance. Use deterministic allocation/I/O properties and reproducible profile-specific measured reports.
- **ALT-008**: Dedicated clock-skew handling adds machinery the selected scope does not require. Keep ordinary UTC/TimeProvider conventions.

Deterministic cost targets are zero avoidable allocations for a synchronous in-memory retained-decoded hit with detailed diagnostics disabled, no payload fetch for successful hot validation, no hot validation preflight for a normal lookup, one indexed small EF lookup/validation round-trip target with reader/sliding extras reported, and no whole-value streaming allocation or full-catalog normal operation. Report inevitable materialization/handle allocations separately and in the total.

Publish measured operations/s and successful entries/s using actual completed item counts/elapsed time. Report failures, misses, cancellations, rejected storage, and incomplete transfers separately. Keep setup/prefill outside timed operations and correctness work inside. Establish same-environment baselines; investigate more than 10-percent throughput/tail-latency regression, lost deterministic I/O properties, or new avoidable hot-hit allocations. Variation above 5 percent makes a 10-percent regression claim inconclusive until repeated measurements reduce noise. These are benchmark review criteria, not unit-test speed thresholds.

## 7. Risks & Assumptions

- **RISK-001**: Ordinal-ignore-case equivalence is stronger than naive invariant lowercase, and database/filesystem rules vary. Test canonicalization against the .NET comparer, store identity format versions, and check digests against persisted identities before returning a value. Do not change normalization in-place on a shared store.
- **RISK-002**: A valid-looking entry can be stale after uncertain publication or recovery. Keep authoritative fence/version/checkpoint state, condition cleanup, report indeterminate outcomes, and fail readiness for unreadable committed metadata instead of reviving older generations.
- **RISK-003**: SMB/NFS server, cache, mount, and failover behavior can violate the assumed native protocol. Qualify exact profiles with real hosts and durability faults. Native readiness probes and mount settings cannot prove the entire cache protocol.
- **RISK-004**: A blocked native I/O call or uncooperative source callback can outlive cancellation and host stop budgets. Bound new admission, retain charged occupied resources, fence late publication, and report stuck/uncertain work. Do not start replacement work merely because a timeout expired.
- **RISK-005**: Strict hot reuse still incurs database/share metadata work. Measure payload/decode savings and validation overhead separately; default off remains meaningful for small values. No provider-outage stale fallback is introduced.
- **RISK-006**: Decoded graph size estimates and references retained by consumers cannot cap the application's entire heap. Require approved immutable/size policies, bound cache-owned reservations, and publish actual process memory separately from accounting estimates.
- **RISK-007**: Cross-contract filter schemas can become incompatible during rolling deployment. Reject known unsafe predicates before mutation and expose any partial work; never silently skip old versions, coerce types, or widen to clear.
- **RISK-008**: Conditional GET/body binding can accidentally bypass authorization or read an excluded collection's request body. Use deferred body parsing after the exposure guard and test with throwing/counting streams and zero provider calls.
- **RISK-009**: Fixed migration artifacts can diverge from configurable schema/prefix names. Validate selected artifacts/model binding and fail readiness on mismatch; host deploys matching changes explicitly. Requests/workers do not repair catalogs.
- **RISK-010**: Required scale/share tests may not be runnable on one workstation. Keep their tasks and qualification state incomplete until actual evidence exists. This is an infrastructure availability limit, not permission to drop a provider/profile from full feature scope.
- **RISK-011**: Benchmark setup, caller-thread allocation counters, OS caches, or weakened durability can make comparisons misleading. Record conditions and actual work, include source/direct-provider baselines, measure concurrent worker allocations, and label inconclusive samples.
- **ASSUMPTION-001**: Decisions D-01 through D-33 and engineering defaults in the reviewed spec are sufficient to implement without another minor-question interview. Resolve routine internal layouts within these contracts; escalate only a material incompatible scope/guarantee change.
- **ASSUMPTION-002**: Stored values are derived disposable data. Source systems remain authoritative, source commits precede invalidation, and reliable invalidation redelivery belongs to the consuming application's established outbox/messaging design.
- **ASSUMPTION-003**: Configuration is fixed for the host lifetime. Operational pause and tracked continuation are runtime commands, not live configuration editing. Registering an integration capability does not authorize its callers.
- **ASSUMPTION-004**: The full scope includes every selected provider, management integration, benchmark report, and qualification target. Intermediate buildable phases do not redefine the product as a reduced release.
