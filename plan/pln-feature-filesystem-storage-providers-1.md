# Introduction

![Status: Implemented](https://img.shields.io/badge/status-Implemented-green)

Add optional filesystem implementations of `IBlobStoreProvider` and `IDocumentStoreProvider`. Preserve existing clients, transformations, behaviors, named registrations, and hosted retention. Support Windows local disk/SMB and Linux local disk/SMB/NFS, with multiple application processes and servers. Require reproducible balanced-workload performance and allocation evidence.

Implementation is complete as of 2026-11-02. This closes the provider, integration, test/probe tooling and documentation work. Deployment and full reference performance qualification remain separate follow-up work in the [qualification checklist](../docs/storage-filesystem-qualification.md). Implemented does not mean every deployment profile has passed.

Source facts were checked on 2026-11-02. The phase descriptions retain the original design and acceptance targets; the execution revision records the delivered APIs and consolidated helper types. Subsequent user authorization separates implementation completion from environment-wide qualification. The task tables track delivered implementation and tooling; profile acceptance is tracked separately. Passing local tests never substitutes for SMB/NFS qualification.

## 1. Requirements & Constraints

- **REQ-001**: Implement `FileSystemBlobStoreProvider` and `FileSystemDocumentStoreProvider` in a new optional `src/Infrastructure.FileSystem` package targeting `net10.0`. Use direct file I/O. Share internal persistence utilities, not `IFileStorageProvider` or one storage provider wrapped around the other.
- **REQ-002**: Preserve `IBlobStoreClient`, `IDocumentStoreClient<T>`, `IBlobStoreProvider`, and `IDocumentStoreProvider` signatures. Reuse existing validation, typed serialization, payload transforms, integrity checks, public token binding, client factories, and behaviors.
- **REQ-003**: Qualify Windows/local, Linux/local, Windows/SMB, Linux/SMB, and Linux/NFS. Test mixed Windows/Linux clients over SMB. Use one share protocol per store. Windows NFS and concurrent SMB/NFS access to one store are excluded. Multiple local processes and multiple remote clients are required.
- **REQ-004**: Default foreground authority-acquisition wait is 5 seconds per store. Zero means fail fast. Honor cancellation during interruptible waits; return a typed busy/timeout failure on exhaustion. This is not an upload limit, authority lease, or guaranteed OS/network-call deadline. Retention skips busy candidates and revisits them.
- **REQ-005**: Default acknowledgement is Durable; Buffered is a per-store opt-in. Both modes retain identical atomicity, ETag, reader, and coordination semantics. Durable success requires payload plus publication/deletion persistence, including references to previously buffered content. Never downgrade an uncertain/failed durable commit to buffered success.
- **REQ-006**: Providers own layout and filenames. Persist original logical keys and verify identity after path lookup. Return one complete generation per record. Stage blob content outside the exclusive publication section; validate conditions again inside it. Metadata-only updates do not read, hash, or rewrite payloads.
- **REQ-007**: Preserve complete blob metadata and all `StoredDocument` fields, including both hashes, copied properties, and transform metadata. Document expiration uses the supplied visibility cutoff; expired physical records still participate in create-only/ETag rules. Blobs remain readable until deleted.
- **REQ-008**: Use live, logical-key-position pagination with existing ordering and token validation. Unchanged datasets have no omissions/duplicates. Concurrent changes can affect later pages. Preserve the document sequence's fixed visibility cutoff without promising a dataset snapshot or snapshot count.
- **REQ-009**: Implement `IBlobStoreRetentionProvider` and `IDocumentStoreRetentionProvider`. Reuse `StorageRetentionOptions`, `BlobRetentionBackgroundService`, and `DocumentRetentionBackgroundService`. Bound candidate discovery as well as deletion, recheck current expiration under authority, preserve active readers, and return confirmed deleted keys/counts.
- **REQ-010**: Return typed expected failures for missing records, conflicts, contention, configuration/format errors, corruption, permissions, capacity, and unavailable storage. An uncertain mutation outcome is explicitly non-retryable by existing automatic retry behaviors. Preserve normal .NET cancellation conventions.
- **REQ-011**: Deliver balanced benchmarks for small records, large blobs, metadata, queries, counts, helpers, and retention, on every supported host/storage combination. Measure successful throughput, p95/p99 latency, allocated bytes, GC, memory, lock contention, and filesystem work. Use Durable for default acceptance; report Buffered separately.
- **SEC-001**: Accept an absolute configured root only. Never use caller keys or token content as filesystem paths. Constrain internal paths, reject unsupported symlink/reparse-point traversal, bound manifest parsing, and do not log content, secrets, or credential-bearing mount settings.
- **SEC-002**: Use existing OS/mount credentials. Never collect or store passwords/tokens in the plan, test configuration, logs, or benchmark evidence. Test harness deletion is restricted to its own marked disposable run directory beneath an explicitly configured scratch root.
- **CON-001**: Add no database, distributed coordinator service, or third-party filesystem dependency. Prefer BCL APIs, but do not claim BCL-only feasibility before Phase 1. If required guarantees cannot be proven within this boundary, record the failed gate and stop dependent implementation without silently changing scope.
- **CON-002**: Do not add public blob lease/range/resumable APIs, provider-native batch interfaces, snapshot history, a public filesystem abstraction, or another hosted retention worker. Existing client multi-key/copy/move helpers continue to work through existing contracts.
- **CON-003**: All top-level builds/tests run sequentially in one worktree. Preserve pre-existing changes to the PRD/ADR and unrelated files. Do not commit, publish packages, push, or open a PR as part of plan execution unless separately requested.
- **GUD-001**: Follow `AGENTS.md`, `.github/copilot-instructions.md`, `.editorconfig`, existing package naming, file-scoped namespaces, disabled nullable annotations, and XML documentation/examples for public symbols. Examples in `/docs` use fictional self-contained models/routes.
- **PAT-001**: Reuse public `BlobStorageBuilderContext.RegisterClient` in `src/Application.Storage/Blobs/BlobStorageBuilderContext.cs:179` and `DocumentStorageBuilderContext.RegisterProvider<T>` in `src/Application.Storage/Documents/DocumentStorageBuilderContext.cs:115`. Keep registration capabilities identical to provider instance capabilities.
- **PAT-002**: Reuse `tests/Application.UnitTests/Storage/Blobs/BlobStoreProviderContractTests.cs:12` through existing compile links in the infrastructure test projects. There is no provider-neutral document contract base; do not derive filesystem tests from the EF-specific document test base.

### Configuration design and first format candidate

The following are explicit initial engineering defaults, not measured performance claims. Phase 1 either validates this candidate or stops dependent work with the failed invariant. Changing the candidate after failure requires a documented plan revision and rerunning its gates; no automatic correctness downgrade is allowed.

| Design symbol or value | Definition |
| --- | --- |
| `FileSystemStorageOptions.RootPath` | Required absolute managed store root. |
| `AccessKind` | Required explicit Local/Smb/Nfs value; compare registration to the store marker rather than claiming reliable protocol autodetection. |
| `CreateRoot` | True by default; false rejects a missing root. |
| `LockAcquireTimeout` | `TimeSpan.FromSeconds(5)`; zero enables fail-fast; negative values are invalid. |
| `Durability` | `FileSystemStorageDurability.Durable` by default; Buffered is the only other value. |
| `TransferBufferSize` | 65,536 bytes by default; positive; pooled for streaming operations and returned on every completion/failure/disposal path. |
| `MaxManifestBytes` | 1,048,576 bytes by default; positive; reject oversized metadata with a typed failure before publication. Keep this configurable and document that it bounds provider metadata, not the existing logical document limit. |
| `MaxQueryMetadataEntries` | 100,000 entries per page/count by default; positive. If a complete correct result cannot be determined within this bound, fail explicitly without returning a partial count or skipping unsurveyed logical keys. |
| `MaxRetentionMetadataEntries` | 10,000 entries examined per sweep by default, additionally bounded by the existing retention request's batch limits; use a persisted internal progress cursor. |
| `FormatVersion` | 1. Root marker `store.json` contains format/version, store GUID, and access kind; initialization must be compatible across processes. |
| Logical identity | Length-prefixed UTF-8 segments using existing normalized keys. Blob identity is kind/container/name; document identity is kind/type/partition/row. Hash with SHA-256, lowercase hex; retain and compare original identities. |
| Candidate paths | `blobs/<container-hash>/<first-two-record-hash-digits>/<record-hash>/current.json`; `documents/<type-hash>/<partition-hash>/<first-two-record-hash-digits>/<record-hash>/current.json`. Payloads are immutable `payload-<generation-guid>.bin` files within the record directory. |
| Candidate manifest | Version, kind, original identity, generation/mutation GUID, payload filename/length, ETag, timestamps, expiration, properties, and the existing blob/document-specific hashes/content-type/transform fields. Parse only generated payload filenames in the record directory. |
| Authority candidate | Stable per-record filesystem coordination identity, shared across local processes and remote clients. Verify server/OS enforcement through loss/reconnect and publication; a separate lockfile plus unchecked manifest rename is not assumed to provide fencing. |
| Query candidate | Direct exact lookup; scan only relevant managed metadata directories for other shapes, retaining at most `Take+1` eligible logical-key candidates in ordinal order. Use the existing final query order and fixed document cutoff. Return typed scan-limit failures before exceeding bounds. |
| Retention candidate | Resumable provider-internal metadata discovery with a persisted cursor and wrap-around. Use per-record non-waiting authority and current-state checks before deletion; do not block foreground operations on a store-wide sweep lock. Prove discovery fairness after updates/crashes. |

Do not promise constant-time prefix queries for this scan-based candidate. For documents, advertise FullMatch as `SupportedEfficiently` and scan-based row-prefix/row-suffix/full-scan/key-listing support honestly as `SupportedClientSide`; preserve `RejectClientSideFilteredQueries` and full-scan opt-ins. `SupportsServerSideCount=false`. If this candidate misses benchmark budgets, add and prove an ordered index in a revised plan before claiming faster prefix access. Do not silently expose unbounded scans. Public token formats and validation remain owned by current clients.

- **ALT-004**: Separate database/coordinator with filesystem payloads. Not part of the agreed dependency boundary. Client serialization/transform costs are reported separately, not subtracted without a measured control. For small-operation throughput use at least 50 percent of equivalent control at equal workload/concurrency. These are plan engineering defaults requiring proof; they are not approved service-level guarantees on unspecified hardware. Never relax them automatically to pass. A missing equivalent control or insufficient samples makes that scenario unavailable, not passed.

Use at least five independently repeated comparison runs in alternating order. Treat an apparent change as inconclusive when its difference is at or below the larger observed inter-run range; record median/min/max and the limiter from a separate diagnostic run. ## 7. Risks & Assumptions

- **RISK-001**: The immutable-manifest plus separate authority candidate may not prevent a previously paused writer from publishing after authority loss, particularly where locks are advisory or reconnect changes handles. Phase 1 must establish enforcement at publication, not assume an application-side check eliminates the race. Failure blocks dependent implementation.
- **RISK-002**: Cross-platform durable namespace publication may need OS-specific operations not exposed by a simple FileStream flush. Buffered/Durable differences must be real, not configuration labels on the same unqualified implementation. Do not claim immunity to disk/controller/server failure beyond tested guarantees.
- **RISK-003**: Two-host share tests, fault injection, and reference storage may not be available on the implementing machine. Local work can complete implementation, but cannot close a remote qualification gate without the required environment and evidence.
- **RISK-004**: Scan-based query pages can inspect O(N) metadata per page and O(P*N) across P pages. The explicit entry budget is an upper bound, not a high-performance claim. If it fails coverage/budgets, index work requires a new proof/plan revision rather than silent unlimited scans or weakened paging order.
- **RISK-005**: Bounded resumable retention can still starve due items under churn unless cursor wrap-around, stale cursor recovery, and busy-key revisits are proven. Metadata updates and candidate discovery must not permanently lose expiration eligibility.
- **RISK-006**: Stable authority files, old generations, rejected staging, and retained uncertain files can grow disk metadata independently of live payload. Report counts/bytes and supported safe reclamation. Never delete shared coordination identities merely to reduce file count while participants may still hold them.
- **RISK-007**: Managed allocation metrics can omit work on other threads/processes or hide required model/payload allocation. Separate process-wide/BDN/provider/client/runner evidence; distinguish pooled/native memory and OS/server cache from managed allocation rate.
- **RISK-008**: Adding errors without updating current retry predicates can replay a committed-but-unacknowledged mutation. TASK-007 and TEST-009 must pass before production writes can run through decorated clients.
- **RISK-009**: Root aliases or server exports can bypass a locally configured protocol restriction. Record supported deployment configuration, validate what is observable, and do not claim universal protocol detection or safety for unqualified access paths.
- **RISK-010**: Proposed per-query bounds and honest client-side capability flags can reject broad/prefix queries at existing default settings. Document the exact required opt-ins and scan-limit failures; never relabel scans efficient merely to bypass validation. MaxManifestBytes is a provider metadata bound and must be tested independently of logical document size.
- **ASSUMPTION-001**: Provider roots are OS-protected, provider-owned, and not concurrently edited by untrusted external filesystem tools. Operators can quiesce all writers/cleanup for the initial whole-root backup procedure. No online backup consistency is assumed.
- **ASSUMPTION-002**: Concrete package/type/API names and engineering defaults in this plan are implementation defaults subject to their stated proof gates. User-agreed policies remain fixed; failed engineering assumptions require an explicit plan revision with evidence, not a silent scope reduction.
- **ASSUMPTION-003**: No live network filesystem, provider implementation, benchmark run, or numerical result was produced during the original planning task. Subsequent execution delivered the implementation and local evidence recorded below; remaining qualification is tracked separately.
