# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

This runbook implements [the public API XML documentation specification](../docs/specs/spec-public-api-xml-documentation-coverage.md). It is an execution procedure, not a replacement for the specification. An agent must execute exactly one bounded documentation batch per session, verify it, update this runbook, and stop for human review.

The specification is the sole source of truth for scope, documentation quality, exclusions, and acceptance criteria. Baseline counts in this runbook are planning data from 2026-08-14; current compiler diagnostics determine the actual work.

## 1. Requirements & Constraints

- **REQ-001**: Add meaningful XML documentation to every undocumented, hand-written public C# symbol under `src/`.
- **REQ-002**: Use compiler warning `CS1591` with documentation generation enabled to discover and verify missing documentation.
- **REQ-003**: Use `.agents/skills/document-code/SKILL.md` for every authoring batch.
- **REQ-004**: Inspect the complete implementation and relevant inherited contracts before writing explicit documentation.
- **REQ-005**: Prefer `<inheritdoc/>` for overrides and interface implementations when inherited documentation accurately describes the contract.
- **REQ-006**: Preserve meaningful existing XML documentation and existing `<inheritdoc/>` comments.
- **REQ-007**: Document public enum members and primary-constructor parameters as required by the specification.
- **REQ-008**: Isolate `src/Common.Utilities/ContentTypes/ContentType.cs` in its own batch.
- **CON-001**: Modify XML documentation comments only. Any code, signature, attribute, formatting, project-file, or behavioral change invalidates the batch.
- **CON-002**: Exclude generated code exactly as defined by the specification, including EF Core migrations and model snapshots.
- **CON-003**: Do not document private or internal symbols unless separately authorized.
- **CON-004**: Do not run documentation batches or top-level builds concurrently in the same worktree.
- **CON-005**: Preserve file encoding and line endings.
- **CON-006**: Do not infer behavior. Record an ambiguity and stop when the public contract cannot be verified.
- **CON-007**: Do not permanently enable documentation generation in project configuration.
- **GOV-001**: Execute one micro-batch per agent session and stop after reporting verification evidence.
- **GOV-002**: A human must approve or commit the completed micro-batch before the next micro-batch begins.
- **GOV-003**: Do not start when the worktree contains unexplained changes overlapping the selected files.
- **GOV-004**: Use current diagnostics rather than treating baseline counts as an allowlist.
- **GOV-005**: Unit and integration tests are not required for comment-only changes. If implementation code changes, restore the code before continuing; tests do not legitimize an out-of-scope code change.

### Definition of a valid in-scope finding

A finding is in scope only when all of these conditions are true:

1. The diagnostic is `CS1591` for a `.cs` file below `src/`.
2. The file is not below `bin/`, `obj/`, or a `Migrations/` directory.
3. The filename does not end in `.g.cs`, `.g.i.cs`, `.generated.cs`, `.designer.cs`, or `ModelSnapshot.cs`.
4. The source file's actual header does not declare `<auto-generated>`.
5. The affected declaration is not marked with `GeneratedCode` or `CompilerGenerated`.
6. The affected declaration is publicly visible.

Do not classify a hand-written source generator as generated merely because a string literal inside it emits an `<auto-generated>` header.

### Agent session contract

Every execution session must use this state machine:

`select task -> audit current target -> select micro-batch -> inspect behavior -> add comments -> verify -> inspect diff -> update ledger -> stop`

Allowed task states are `Pending`, `In progress`, `Blocked`, and `Completed`.

- Set a project task to `In progress` after its first verified micro-batch.
- Keep it `In progress` while current in-scope findings remain.
- Set it to `Blocked` only when a specific ambiguity or external failure prevents safe progress; record the exact blocker.
- Set it to `Completed` only after a fresh project audit reports zero in-scope findings.

### Per-session batch procedure

Execute these steps literally for one project task at a time.

#### Step A — Select the next task

1. Select the first task in numeric order whose state is `Pending` or `In progress`.
2. Re-read the specification sections `Scope`, `Documentation Requirements`, `Change Constraints`, `Batch Workflow`, and `Acceptance Criteria`.
3. Re-read `.agents/skills/document-code/SKILL.md` completely.
4. Run `git status --short` and `git diff --stat`.
5. If selected files overlap unexplained user changes, stop and report the overlap. Preserve all unrelated changes.

#### Step B — Generate current findings

From the repository root, set the selected project path and use a temporary log outside the repository:

```powershell
$ProjectPath = 'src/Common.Abstractions/Common.Abstractions.csproj'
$AuditLog = Join-Path $env:TEMP 'bitdevkit-xml-doc-audit.log'

dotnet build $ProjectPath `
  --nologo `
  --no-restore `
  /p:UseSharedCompilation=false `
  /p:GenerateDocumentationFile=true `
  /p:TreatWarningsAsErrors=false `
  "/p:WarningsAsErrors=" 2>&1 |
  Tee-Object -FilePath $AuditLog
```

If `--no-restore` fails solely because restore outputs are missing, run `dotnet restore $ProjectPath --nologo` once and repeat the build. Do not suppress unrelated build failures.

Extract the diagnostic locations:

```powershell
$Findings = Select-String -Path $AuditLog -Pattern '^(.+\.cs)\((\d+),(\d+)\): warning CS1591:' |
  ForEach-Object {
    if ($_.Line -match '^(.+\.cs)\((\d+),(\d+)\): warning CS1591: Missing XML comment for publicly visible type or member ''(.+)''') {
      [pscustomobject]@{
        Path = [System.IO.Path]::GetFullPath($Matches[1])
        Line = [int]$Matches[2]
        Column = [int]$Matches[3]
        Symbol = $Matches[4]
      }
    }
  } |
  Sort-Object Path, Line, Column -Unique

$Findings | Format-Table Path, Line, Symbol -AutoSize
```

Classify each finding with the generated-code rules in Section 1. Do not rely only on filename matching for semantic attributes. Record every exclusion with its path, line, and exclusion rule. The remaining ordered collection is `$InScopeFindings`.

For TASK-113, remove findings whose normalized path ends with `src\Common.Utilities\ContentTypes\ContentType.cs`. For TASK-114, retain only that file.

#### Step C — Select one deterministic micro-batch

1. Sort `$InScopeFindings` by normalized path, then line, then column.
2. Select the first file with a remaining finding.
3. Select consecutive files from the same project, stopping before either limit would be exceeded:
   - maximum 6 files; or
   - maximum 80 findings.
4. Never split one file across micro-batches. If the first file exceeds 80 findings, select that file alone.
5. TASK-114 is the explicit exception: select the complete `ContentType.cs` file as one dedicated batch.
6. Record the exact selected paths and pre-change finding count before editing.

These limits are maximums, not targets. Use a smaller batch when implementation analysis requires substantial dependency tracing.

#### Step D — Author documentation

For every selected finding:

1. Determine whether meaningful documentation or `<inheritdoc/>` was added by another change after the audit; if yes, skip it.
2. Resolve overridden and implemented members first. Add only `<inheritdoc/>` when the inherited contract is meaningful and accurate.
3. Otherwise inspect the complete implementation and only those dependencies that materially affect the public contract.
4. Add the smallest accurate XML comment satisfying DOC-001 through DOC-012 in the specification.
5. Document `Result` outcomes, cancellation, retries, exceptions, side effects, persistence, ordering, and lifecycle only when observable and verified.
6. Add examples only where the specification says they materially help consumers.
7. For TASK-114, derive MIME type and text/binary semantics from each member's existing `ContentTypeMetadate` value; do not alter enum members or attributes.
8. If behavior is ambiguous, do not guess. Leave that symbol unchanged, mark the task `Blocked`, record the path, symbol, inspected evidence, and ambiguity, then stop.

#### Step E — Verify the micro-batch

1. Repeat the targeted build command from Step B.
2. Regenerate and filter findings using the same rules.
3. Confirm every selected file has zero in-scope `CS1591` findings.
4. Confirm no invalid XML documentation warning was introduced, including `CS0419`, `CS1570`, `CS1572`, `CS1573`, `CS1574`, `CS1584`, `CS1658`, or another unresolved `cref` warning.
5. Run `git diff --check`.
6. Run `git diff -- <selected paths>` and inspect every hunk.
7. Confirm changed C# lines are XML documentation lines only and no existing meaningful comment was rewritten.
8. Run `git status --short` and compare it with the pre-batch state. Investigate any generated or unrelated artifact before reporting success.

Do not run unit or integration tests for a valid comment-only micro-batch. If the diff contains implementation changes, restore only those changes, re-run verification, and do not mark the batch complete until the diff is comment-only.

#### Step F — Update state and stop

Append one row to the execution log using the schema below.

- If current in-scope findings remain in the project, set its task state to `In progress`.
- If none remain, perform one fresh targeted audit and then set its task state to `Completed` with the date.
- Report the task ID, selected files, before/after finding counts, generated exclusions, verification commands, build result, diff result, and any ambiguity.
- Stop. Do not select another micro-batch in the same session.

## 3. Alternatives

- **ALT-001**: Document all 7,710 baseline findings in one session. Rejected because it prevents implementation-level review, increases semantic drift, and violates the specification's bounded-delivery requirement.
- **ALT-002**: Generate comments mechanically from signatures. Rejected because signatures do not establish validation, result, cancellation, side-effect, or lifecycle semantics.
- **ALT-003**: Permanently enable XML documentation generation in project files. Rejected because the specification authorizes command-line audit properties only.
- **ALT-004**: Suppress `CS1591`. Rejected because suppression hides missing coverage rather than implementing it.
- **ALT-005**: Copy interface or base documentation into implementations. Rejected because `<inheritdoc/>` preserves a single authoritative contract.
- **ALT-006**: Run projects in parallel agents sharing one worktree. Rejected because build outputs and overlapping edits make verification unreliable.

## 7. Risks & Assumptions

- **RISK-001**: Baseline counts drift as other work changes `src/`. Mitigation: regenerate findings before every batch.
- **RISK-002**: Generic prose passes `CS1591` but misleads consumers. Mitigation: inspect implementation and inherited contracts for every symbol.
- **RISK-003**: Generated code is falsely selected. Mitigation: combine path, filename, header, and declaration-attribute checks.
- **RISK-004**: A build changes generated example artifacts or line endings. Mitigation: compare status before and after, inspect hashes/diffs, and never discard unrelated changes.
- **RISK-005**: Large batches hide non-comment changes. Mitigation: enforce micro-batch limits and inspect every diff hunk.
- **RISK-006**: Documentation duplicates inherited contracts. Mitigation: resolve interface and base members before explicit authoring.
- **RISK-007**: The dedicated content-type catalogue is too large for reliable review. Mitigation: isolate it, use metadata as its behavioral source, and review it independently.
- **ASSUMPTION-001**: Baseline project names and paths remain valid; Phase 0 must update the queue if the current repository differs.
- **ASSUMPTION-002**: Documentation generation via command-line MSBuild properties continues to surface `CS1591` without project-file changes.
- **ASSUMPTION-003**: Human review or commit boundaries keep each agent session's diff attributable to one micro-batch.
