# Introduction

![Status: Implemented with deviations](https://img.shields.io/badge/status-Implemented%20with%20deviations-yellow)

This plan validates and completes Document Storage using the lifetime, validation, cancellation, continuation-token, concurrency, expiration/retention, provider-ownership, observability, and test patterns proven by Blob Storage. Document Storage remains the typed JSON-document API; Blob Storage remains the streaming binary-object API. Document Storage is new and has no backward-compatibility requirement, so this plan removes obsolete contracts and performs clean API corrections without compatibility wrappers. Proven storage-neutral primitives are extracted into Common packages, while storage-specific orchestration remains in Application Storage.

## Implementation Decisions

- The dedicated `AzureBlobDocumentStoreProvider` is retained. The finalized `IBlobStoreClient` supports conditional deletion but does not expose conditional upload with `IfMatchETag`; an adapter would therefore turn atomic document replacement into a read-then-write race. The retained provider still follows account-only ownership: it accepts `BlobServiceClient`, derives a deterministic container, creates or reuses it through `AsyncInitializationGate`, and never deletes it during disposal.
- `PeriodicBackgroundService` and `PeriodicBackgroundServiceOptions` are shared by Blob and Document retention. Storage-specific sweep contracts and Result mapping remain in Application Storage.

## 1. Requirements & Constraints

- **REQ-001**: Keep `IDocumentStoreClient<T>` typed and document-oriented; do not expose streams or blob transfer operations through it.
- **REQ-002**: Rename Result-returning operations to `GetAsync`, `FindPageAsync`, `ListPageAsync`, `CountAsync`, `ExistsAsync`, `UpsertAsync`, `UpsertManyAsync`, and `DeleteAsync`; remove all `*ResultAsync` methods without obsolete wrappers.
- **REQ-003**: Return provider-neutral document metadata. `GetAsync` and `FindPageAsync` return `DocumentEntry<T>` values containing `DocumentKey`, `Value`, `ETag`, `ContentHash`, `CreatedAt`, `LastModifiedAt`, `ExpiresAt`, and a cloned `PropertyBag`. `UpsertAsync` and metadata updates return `DocumentInfo` with the same metadata except the payload.
- **REQ-004**: Add optimistic concurrency through `DocumentWriteOptions.IfMatchETag`, `DocumentWriteOptions.CreateOnly`, and `DocumentDeleteOptions.IfMatchETag`. Map failed conditions to `DocumentStoreConflictError`.
- **REQ-005**: Define bulk upsert as ordered and non-atomic across the complete input. Validate and materialize the complete input before the first write, process items in input order, and stop after the first failed item. Return `Result<DocumentBatchResult<DocumentInfo>>` containing successful items and the failed key when a provider cannot complete the batch. Never return an unqualified failure after earlier writes succeeded.
- **REQ-006**: Centralize serialization in `DocumentStoreClient<T>`. Providers persist and return `StoredDocument` byte payloads and must not serialize application types or depend on generic provider methods.
- **REQ-007**: Add `DocumentStoreOptions.MaxDocumentSize` with the default `ByteSize.Megabytes(1)`. Enforce the logical serialized size before provider I/O and expose a provider stored-size limit through capabilities when a backend has a lower limit.
- **REQ-008**: Preserve bounded continuation paging, explicit full-scan opt-in, deterministic key ordering, key-only listing, and provider capability checks.
- **REQ-009**: Resolve `IContinuationTokenProtector` in the document client. Protected configurations must reject unsigned, modified, wrong-purpose, wrong-provider, and query-mismatched tokens.
- **REQ-010**: Use one `DocumentStorageBuilderContext`. Remove `DocumentStoreBuilderContext<T>`, Scrutor descriptor rewriting, behavior re-registration, manual `ActivatorUtilities` accessor creation, and direct provider-instance registration overloads.
- **REQ-011**: Register each provider, typed client, and dashboard accessor as keyed DI services using the configured singleton, scoped, or transient lifetime. `DocumentStoreClientFactory` is a scoped lookup-only resolver.
- **REQ-012**: Build each typed client as provider adapter, configured behaviors, outer validating/serializing `DocumentStoreClient<T>`. Invalid keys, queries, entities, batches, and options must not reach behaviors or providers.
- **REQ-013**: Support multiple named clients for the same CLR document type. Require a unique case-insensitive `(typeof(T), clientName)` pair, use `"default"` for the unnamed convenience registration, and allow at most one registration per type to be marked as the default. Register unkeyed `IDocumentStoreClient<T>` only for that explicit default; resolve every named client through `IDocumentStoreClientFactory.CreateClient<T>(name)`.
- **REQ-014**: Add `DocumentStoreClientBehaviorBase<T>` and `DocumentStoreOperationContext` so logging, metrics, retry, timeout, cache, and chaos behaviors share operation naming and key/query context without duplicating forwarding methods.
- **REQ-015**: Timeout behavior must pass its linked token to the operation, cancel and await the operation to quiescence, preserve caller `OperationCanceledException`, return `DocumentStoreTimeoutError` for elapsed deadlines, and use injected `TimeProvider`.
- **REQ-016**: Retry behavior must not retry validation, caller cancellation, timeout, serialization, not-found, conflict, or size-limit failures. A retry must not overlap a prior attempt.
- **REQ-017**: Log full raw document keys by default with typed `ILogger<T>`. Add a configurable safe key-display strategy only for deployments that classify keys as sensitive. Do not log document payloads, encryption material, or continuation-token contents.
- **REQ-018**: Add provider-neutral payload transforms through a public `IDocumentPayloadTransform` contract. Execute transforms in registration order for writes and reverse order for reads; reserve `bdk_`-prefixed metadata keys.
- **REQ-019**: Provide compression and encryption transforms using `CompressionHelper`, `EncryptionHelper`, `IEncryptionKeyProvider`, `StreamHelper`, `TemporaryFileHelper`, and `Base64UrlHelper`. Encryption writes use the active key and reads resolve the persisted key ID.
- **REQ-020**: Add provider-neutral document expiration and retention. Add typed copy and move as client extensions, not provider operations; keep stream/file transfers out of Document Storage.
- **REQ-021**: Replace `AzureBlobDocumentStoreProvider` with a provider-neutral `BlobDocumentStoreProvider` adapter over `IBlobStoreClient`. Encode type, partition key, and row key as independent Base64Url path segments so all valid document keys round-trip without reserved separators.
- **REQ-022**: The blob-backed adapter must inherit atomic upload, conditional write/delete, ETag, paging, cancellation, and provider initialization behavior from Blob Storage instead of duplicating Azure Blob SDK logic.
- **REQ-023**: Entity Framework providers must depend on root `IServiceScopeFactory`, create and own one scope and `TContext` per operation, and remove caller-owned context constructors and every `ChangeTracker.Clear()` call.
- **REQ-024**: EF entity mapping remains annotation-based on `StorageDocument`. Persist payload bytes, transform metadata, content hash, timestamps, and concurrency version on the entity; no separate fluent entity configuration is introduced.
- **REQ-025**: In-memory storage must keep synchronization and backing collections private, store copied byte payloads, and return cloned records so caller mutation cannot modify persisted state.
- **REQ-026**: Azure Table and Cosmos providers must use async resource initialization owned by the provider, conditional ETag operations, typed provider errors, and non-cancelable compensation or rollback where multi-step mutations can partially apply.
- **REQ-027**: Azure Table payload storage must split bytes into `ByteSize.Kilobytes(60)` chunks named `bdk_content_0000`, `bdk_content_0001`, and so on; persist `bdk_content_chunk_count`; validate the complete entity against the 1 MiB Azure Table entity limit before submission; and atomically replace one entity per document. All chunk and transform metadata keys use `bdk_` prefixes.
- **REQ-028**: Cosmos persistence must expose and enforce the Cosmos ETag, use the provider-neutral serialized payload envelope, and preserve native continuation state only inside protected document continuation tokens.
- **REQ-029**: Remove production `internal` declarations from Document Storage. Keep implementation details private; make required cross-file routes public through `DocumentStorageDashboardRoutes` with XML documentation and examples.
- **REQ-030**: Dashboard document mutations require the existing dashboard endpoint authorization and antiforgery conventions. Do not add a second document-specific authentication model.
- **REQ-031**: Keep `DocumentStoreCacheProvider`, but migrate it to the corrected client API and make its invalidation and conditional-write behavior explicit. Do not merge `ICacheProvider` with Document Storage.
- **REQ-032**: Update `docs/features-storage-documents.md` and `docs/specs/spec-application-storage-documents-paging.md` to describe the final contract, alignment boundaries, provider limits, concurrency, transforms, and batch semantics.
- **REQ-033**: Add `ExpiresAt` to `DocumentEntry<T>`, `DocumentInfo`, `StoredDocument`, and persistence entities. Normalize timestamps to UTC. Exact reads and existence checks use the operation's `TimeProvider.GetUtcNow()` cutoff and treat due documents as not found. Count uses its operation cutoff. A page sequence stores its first-page visibility cutoff in the protected continuation token and uses that fixed cutoff for every continuation page, producing stable page semantics while physical deletion remains asynchronous.
- **REQ-034**: Add `DocumentWriteOptions.Expiration` using the common `ExpirationChange` value object. Default to `Preserve`; preserve the existing expiration on updates and produce no expiration on inserts. Support explicit `Set`, `Clear`, and `After(TimeSpan)` operations; resolve relative expiration once using the injected `TimeProvider` before provider I/O.
- **REQ-035**: Expose shared `StorageRetentionOptions` through `DocumentStorageOptions.Retention` and `BlobStorageOptions.Retention` with the existing Blob Storage defaults: enabled, 15-second startup delay, one-hour sweep interval, batch size 1000, maximum 10 batches per client, zero batch delay, and 10-second stop timeout.
- **REQ-036**: Add `IDocumentStoreRetentionProvider` outside the public document client. All providers must exclude due documents from exact reads, existence, count, and pages using the supplied visibility cutoff. Retention-capable providers must use indexed/native expiration queries and ETag, lease, or transaction protection; the hosted service must never emulate physical cleanup through public query scans.
- **REQ-037**: Register a monitored `DocumentRetentionBackgroundService` through `AddDocumentStorage`. Resolve each keyed provider in a fresh DI scope, skip unsupported providers, use `TimeProvider`, expose `SweepOnceAsync`, and treat already-deleted documents as successful idempotent cleanup.
- **REQ-038**: Move the storage-neutral expiration model and helpers to Common: `ExpirationChange` and `ExpirationChangeMode` in `Common.Abstractions`, and `ExpirationHelper` in `Common.Utilities`. Blob property patch helpers and Document Storage must both consume them without changing Blob Storage's persisted expiration format.
- **REQ-039**: Move proven cross-feature helpers to Common and migrate both Blob and Document Storage in the same change: `PeriodicBackgroundService` and options for monitored startup/interval/shutdown execution, `ContentHashHelper` for canonical `sha256:<lowercase-hex>` values, `IKeyDisplayStrategy` with raw and SHA-256 implementations, and `ContentTransformEnvelopeCodec` for versioned `bdk_` transform metadata.
- **REQ-040**: Keep provider registration, Result error mapping, retention provider interfaces, sweep coordination, and operation behavior bases in `Application.Storage`; these concepts depend on storage contracts and must not move into `Common.Abstractions` or `Common.Utilities`.
- **REQ-041**: Document all new Common APIs in `docs/common-utilities.md` and `docs/common-serialization.md`; update `docs/features-storage-blobs.md` for the shared primitives without changing Blob behavior; document document expiration/retention configuration, timing semantics, provider support, and multi-node behavior in both Document Storage documents.
- **REQ-042**: Add `UpdatePropertiesAsync(DocumentPropertiesUpdate)` for metadata-only mutation. A null `Properties` value preserves the current property bag; a non-null bag replaces it. `ExpirationChange` defaults to preserve, `IfMatchETag` is optional, the payload and logical `ContentHash` remain unchanged, and providers must apply metadata changes atomically or return `DocumentStorePartialUpdateError` after failed compensation.
- **REQ-043**: Always compute and persist canonical SHA-256 hashes for both logical serialized content and stored transformed content. Verify the stored hash before reverse transforms and the logical hash before deserialization. Expose only the logical `ContentHash`; support optional `DocumentWriteOptions.ExpectedContentHash` and fail before commit with `DocumentStoreIntegrityError` on mismatch.
- **REQ-044**: Named registrations carry name, default status, provider, capabilities, lifetime, and type identity. Factories, dashboard, diagnostics, health checks, continuation-token provider binding, cache keys, and retention registrations must include the normalized client name so same-type clients cannot collide.
- **REQ-045**: Add `EnumerateAsync` as an extension over `FindPageAsync` and `EnumerateKeysAsync` over `ListPageAsync`. Require `DocumentEnumerationOptions.MaxItems` to be greater than zero for every enumeration, stop without requesting another page after the limit, preserve cancellation, and never expose provider-native tokens.
- **REQ-046**: Add core `DeleteManyAsync(IReadOnlyCollection<DocumentDelete>)` with complete prevalidation, ordered execution, per-item optional ETags, and explicit partial completion. Add maintenance extension `DeleteByQueryAsync` with mandatory positive `MaxItems`, optional `Take`, `DryRun`, `AllowFullScan`, and `ContinueOnError`; it must use bounded key pages and conditional deletes, never materialize payloads.
- **REQ-047**: Add `IDocumentStorageDiagnosticsService`, immutable snapshot/client diagnostic models, and a Document Storage MCP diagnostics handler. Report names, defaults, lifetimes, provider capabilities, maximum sizes, transform identifiers, conditional-write support, expiration/retention support, health, and last retention outcome; never expose payloads, raw continuation tokens, encryption keys, or transform secrets.
- **REQ-048**: Add `CopyAsync` and `MoveAsync` extensions between any two `IDocumentStoreClient<T>` instances. Preserve properties and expiration by default, support explicit target expiration/property overrides and create-only/overwrite behavior, reserialize through the target client, and return `DocumentTransferResult` containing source and target metadata.
- **REQ-049**: A move to the same client and key is a successful no-op after confirming logical existence. Other moves copy first and conditionally delete the source using the ETag read for the copy. If the source changed, retain it and return `DocumentStoreTransferError` stating that the target exists and the source was not deleted.
- **REQ-050**: Expired documents are hidden from reads, queries, enumeration, and copy/move sources but remain physical records until retention. `CreateOnly` conflicts with an expired physical record. Upsert with preserved expiration leaves it expired; upsert or metadata update with cleared/future expiration revives it. Delete remains idempotent and may remove an expired physical record.
- **REQ-051**: Azure Blob-backed and Azure Table document registrations require only account-level connectivity: a `BlobServiceClient` or `TableServiceClient` resolved from DI or equivalent account connection settings. Do not require callers to create or pass `BlobContainerClient`, `TableClient`, container names, or table names.
- **REQ-052**: Derive resource names deterministically from `normalizedClientName + "\n" + documentTypeIdentity`. Use default Blob container name `bdk-doc-{first 32 lowercase hexadecimal characters of SHA-256(input)}` and default Table name `BdkDoc{first 32 lowercase hexadecimal characters of SHA-256(input)}`. Permit only an optional validated provider prefix override; no resource-name configuration is required.
- **REQ-053**: Providers own asynchronous idempotent resource initialization. Before every operation, an initialization gate must ensure the derived container/table exists using `CreateIfNotExistsAsync`. Concurrent callers and application nodes may race safely; successful initialization is cached per provider instance, while cancellation or failure is not cached and a later call retries.
- **REQ-054**: Initialization must work against an existing storage account and reuse an existing derived resource without mutating unrelated account resources. Provider disposal and application shutdown must never delete containers or tables. Permission, naming, and service failures map to typed provider errors and appear in health/diagnostics output without connection secrets.
- **CON-001**: No stored-data migration or public API compatibility layer is required. Tests create fresh stores and containers.
- **CON-002**: Do not change finalized Blob Storage semantics while adding the blob-backed document adapter. Run the complete Blob Storage contract suite as regression coverage.
- **CON-003**: Public symbols require XML documentation and usage examples according to repository policy.
- **PAT-001**: Follow `BlobStorageBuilderContext`, `BlobStoreClientRegistration`, `BlobStoreClientFactory`, `BlobStoreClient`, and Blob behavior implementations for DI, validation, cancellation, telemetry, and continuation-token structure.
- **PAT-002**: Reuse existing common helpers; do not introduce a generic storage framework unless at least Blob Storage and Document Storage both consume the extracted code in this change.

## 3. Alternatives

- **ALT-001**: Keep generic providers and provider-local serialization. Rejected because it duplicates serialization, hashing, compression/encryption, size enforcement, and mutable-object handling across five providers.
- **ALT-002**: Make Document Storage a thin alias over Blob Storage. Rejected because typed serialization, partition/row queries, count, key-only pages, and document batch semantics are not blob concerns.
- **ALT-003**: Keep `*ResultAsync` names because methods return `Result`. Rejected because Blob Storage established the repository convention that the return type communicates Result semantics without a method-name suffix.
- **ALT-004**: Hide provider concurrency and continue returning only `T`. Rejected because EF, Azure Table, Cosmos, and Azure Blob already have concurrency tokens; hiding them forces unsafe last-write-wins behavior.
- **ALT-005**: Promise globally atomic multi-document writes. Rejected because Azure Blob, cross-partition Azure Table, and cross-partition Cosmos cannot provide that guarantee consistently.
- **ALT-006**: Generalize Blob and Document behavior bases into one common storage behavior framework. Rejected for now because their operation contracts and data ownership differ; only proven common utilities are reused.
- **ALT-007**: Retain the dedicated Azure Blob document implementation. Rejected because `BlobDocumentStoreProvider` can reuse the finalized Blob Storage atomicity, ETag, paging, initialization, and cancellation behavior for every blob backend.
- **ALT-008**: Depend only on native Cosmos TTL or Azure lifecycle policies. Rejected because in-memory, EF, Azure Table, and blob-backed providers require one provider-neutral expiration contract and deterministic retention behavior.
- **ALT-009**: Re-evaluate the wall clock independently on every continuation page. Rejected because provider-native continuation tokens may be query-bound and items would shift eligibility during one logical page sequence; the first-page cutoff provides stable snapshot visibility while new operations hide newly expired documents immediately.
- **ALT-010**: Move all retention and behavior infrastructure into Common packages. Rejected because keyed storage-provider resolution, Result errors, capabilities, and sweep summaries are Application Storage concepts rather than generally reusable utilities.
- **ALT-011**: Keep one client per CLR document type. Rejected because primary/archive, regional, migration, and tenant-specific stores require multiple providers for the same document model; an explicit default preserves ergonomic direct DI without ambiguity.
- **ALT-012**: Implement document copy/move and query deletion as provider methods. Rejected because the operations can be composed safely from the client API, must cross providers, and should not enlarge the minimum provider contract beyond optimized single/batch primitives.
- **ALT-013**: Require applications or deployment scripts to pre-create Azure document containers/tables and pass resource clients. Rejected because the provider owns its persistence resources, account-level connectivity is sufficient, and idempotent `CreateIfNotExistsAsync` works for both existing and new resources.

## 7. Risks & Assumptions

- **RISK-001**: Central serialization changes every provider persistence representation. Mitigation: no compatibility is required, tests create fresh resources, and provider contracts are implemented before provider-specific optimizations.
- **RISK-002**: Azure Table payload chunking approaches the service entity-size limit after metadata overhead. Mitigation: calculate the complete serialized entity size before submission and expose the effective provider limit.
- **RISK-003**: Singleton document clients can capture scoped serializers, behaviors, or key providers if registration is incorrect. Mitigation: enable scope validation tests and require dependencies to be valid for the selected client lifetime.
- **RISK-004**: Batch behavior differs by provider. Mitigation: expose capabilities and always return explicit completed/failed item state; never imply global atomicity.
- **RISK-005**: A blob-backed document client can accidentally apply compression or encryption twice. Mitigation: document transform order and reject duplicate transform identifiers in the document payload envelope; Blob transforms remain independently configured.
- **RISK-006**: Retrofitting a generic common behavior framework could destabilize finalized Blob Storage. Mitigation: reuse existing common primitives and duplicate small domain-specific orchestration until a second proven implementation justifies extraction.
- **RISK-007**: Retention is asynchronous, so due documents remain physically stored after becoming logically invisible. Mitigation: enforce visibility cutoffs on every new read/query operation, document continuation snapshot semantics, provide `SweepOnceAsync`, and allow shorter cleanup intervals.
- **RISK-008**: A retention sweeper can race with an update that extends or clears expiration. Mitigation: select the ETag/concurrency version with each due candidate and conditionally delete only that version.
- **RISK-009**: Cosmos TTL rounds to seconds and deletion is service-scheduled. Mitigation: persist the exact UTC `ExpiresAt`, round item TTL upward, and describe native deletion as eventually consistent.
- **RISK-010**: Extracting Blob helpers could change public behavior or persisted metadata. Mitigation: preserve existing formats and keys, delegate old Blob-specific facades where necessary, and run all Blob regression and retention contracts.
- **RISK-011**: A continuation sequence can return a document whose expiration passed after the first page was requested. Mitigation: define the sequence as one snapshot at its protected first-page cutoff; new operations use a new cutoff and hide the document.
- **RISK-012**: Named clients can cause accidental writes to the wrong backend. Mitigation: require explicit names for factory resolution, allow only one explicit default per type, include the client name in logs/tokens/cache keys, and display it prominently in diagnostics/dashboard views.
- **RISK-013**: Copy/move and query deletion can partially mutate multiple stores. Mitigation: use explicit result models, target-first copy semantics, source ETag deletion, mandatory query limits, dry-run support, and complete partial-failure reporting.
- **RISK-014**: Logical hashes depend on serializer configuration and document shape. Mitigation: hash the exact serialized bytes produced by the registered client, bind expected hashes to that representation, and reserialize/recompute when crossing clients.
- **RISK-015**: Account credentials may allow data access but not container/table creation. Mitigation: fail initialization with a typed provider error naming the derived resource and required operation, surface it in health/diagnostics, never log credentials, and retry on a later operation after permissions change.
- **RISK-016**: Deterministic resource naming can collide if identity input is normalized inconsistently. Mitigation: normalize client names once, use the persisted document type identity verbatim, hash canonical UTF-8 input, centralize naming in `AzureDocumentResourceName`, and contract-test all registrations.
- **ASSUMPTION-001**: Document Storage has no external consumers, stored-data migration requirement, or API compatibility requirement.
- **ASSUMPTION-002**: Applications may register multiple named providers for the same `T`; direct `IDocumentStoreClient<T>` injection is available only when one registration is explicitly marked as default.
- **ASSUMPTION-003**: Document queries remain key-based only; arbitrary payload-property querying and sorting are outside this plan.
- **ASSUMPTION-004**: A 1 MiB logical document default is acceptable and can be reduced per registration or by provider capabilities.
- **ASSUMPTION-005**: Dashboard authentication continues to be owned by the shared dashboard endpoint options.
- **ASSUMPTION-006**: Document expiration is an immediate logical visibility boundary for new operations plus eventual physical deletion; a continuation sequence intentionally retains its first-page visibility cutoff.
- **ASSUMPTION-007**: The supplied Azure storage-account identity has permission to create and use Blob containers or Tables; no subscription/resource-group management-plane permissions are required.
