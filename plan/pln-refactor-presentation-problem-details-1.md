# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

Replace Hellang in `Presentation.Web` with ASP.NET Core exception handling and status-code pages. Share the DevKit error format across thrown exceptions and failed Results in Minimal APIs and MVC. Capture the current HTTP behavior first. Prove mixed API and HTML routing and the generated OpenAPI contract in `Presentation.TestHost` before migrating the consuming hosts and removing the package.

Paths are relative to the repository root. A task can start once its listed dependencies pass. Tasks that write the same file run in task order. Run top-level restore, build, and test commands sequentially in the worktree. Mark a task complete and record its completion date after its listed validation passes.

## 1. Requirements & Constraints

- **REQ-001** Configure the combined feature with `AddResponseProblemDetails()` or `AddResponseProblemDetails(Action<ProblemDetailsOptions>)`. Put the options type in `BridgingIT.DevKit.Presentation.Web.Errors`. The wrapper `UseResponseProblemDetails()` installs native `UseExceptionHandler()` and then `UseStatusCodePages()`. Either native middleware can be activated independently.
- **REQ-002** Set `IncludeExceptionDetails=false`, `ShouldHandleRequest=null`, `OnBeforeWriteDetails=null`, `ShouldLogUnhandledException=true`, and `ShouldLogResultErrors=false` by default. `ShouldHandleRequest` is `Func<HttpContext, bool>`. `OnBeforeWriteDetails` is `Action<HttpContext, Microsoft.AspNetCore.Mvc.ProblemDetails>`. Provide a case-insensitive `ISet<string>` for `AllowedHeaderNames` with the defaults in REQ-008.
- **REQ-003** Support `Map<TException>` and `MapDefault<TException>`, each returning DevKit `ProblemDetailsOptions` with `where TException : Exception`. Both accept `int statusCode, string title = null, string typeUri = null`, `Func<TException, Mvc.ProblemDetails> factory`, or `Func<TException, HttpContext, Mvc.ProblemDetails> factory, Func<TException, HttpContext, bool> when = null`, where `Mvc` denotes `Microsoft.AspNetCore.Mvc`. Evaluate host mappings, module mappings, built-ins, and catch-all in that order. Within each group, first matching declaration wins, including base types. False predicates continue. Require 400–599 and a non-null problem. Invalid static configuration fails at startup. Invalid or failing factories follow the framework failure path.
- **REQ-004** Keep the status, title, and public detail in the table below for built-in exception mappings. Use `https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/{status}` and omit `instance` by default. Preserve an explicit mapping's value. Handle `NotSupportedException` as an ordinary 500 before the response starts. Use native propagation once the response has started.
- **REQ-005** Keep Minimal API Result classification in `ResultMapHttpExtensions`. The default order is forbidden (403), unauthorized (401), not found (404), validation (400), conflict (409), concurrency (409), domain policy (400), cancellation (499), timeout (504), exception (500), rule exception (500), rule (500), fallback (500). Reuse this path for MVC failures, including custom handlers. Preserve success paths, explicit typed result arms, ordinary MVC responses and formatters, and automatic `[ApiController]` validation with native top-level `errors`.
- **REQ-006** Use `data.errors` as a map of field names to arrays of messages. Strip a leading `Entity.` case-insensitively, preserve remaining case, group blank names under `validation`, and omit an empty error map. Include `data.result` only where the existing Result mapper exposes it and the Result carries no exception diagnostics. Omit empty `data`. Keep the ordinary Result identifiers, titles, type URIs, and `instance` behavior, including the ID created for an unclassified failure.
- **REQ-007** Keep native writer selection in registration order. For an accepted writer, preserve application extensions and run applicable native customization and the final DevKit hook once. Use the mapping, handler, or existing empty response status for HTTP status, body `status`, and logging. Restore it after enrichment. When all writers decline an in-scope automatic exception or empty status, write public `application/problem+json` with identifiers and validation using host HTTP JSON settings. When all writers decline a mapped Result, keep `ProblemHttpResult` JSON fallback and its existing mapper-provided extensions. Both fallback paths omit optional diagnostics and skip write hooks. A writer or hook failure produces no second write.
- **REQ-008** Keep `traceId` separate from `correlationId`. For automatic exceptions use the request correlation ID then `TraceIdentifier`. For Results use request correlation, ambient `CorrelationId.Current`, Activity trace ID, then `TraceIdentifier`. Keep native trace behavior based on `Activity.Current?.Id ?? context.TraceIdentifier`. Preserve existing exception/status cache prevention and the case-insensitive response header allowlist `CorrelationId`, `FlowId`, `TraceId`, `WWW-Authenticate`, `Strict-Transport-Security`, `Access-Control-Allow-Credentials`, `Access-Control-Allow-Headers`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Origin`, `Access-Control-Expose-Headers`, and `Access-Control-Max-Age`. Retain configured extra response headers without copying request headers.
- **REQ-009** Scope automatic DevKit exception and empty-status handling using `ShouldHandleRequest`. Use the original request path or endpoint during exception re-execution. Keep explicit Result mapping and MVC model validation independent of this predicate. Preserve host native HTML exception and status pages, native status-code overrides and disable features, and framework eligibility rules. Only eligible empty 400–599 responses receive default status problems. The type is `https://httpstatuses.io/{status}` and the title is the reason phrase. A declared content type or any declared length, including zero, keeps control with the existing response.
- **REQ-010** Keep `AddResultHttpProblemDetails(bool)` and `ResultHttpProblemDetailsOptions` for Result-only hosts. When combined and Result-only registrations coexist, the final combined disclosure setting wins in both orders. Keep Microsoft's `AddProblemDetails()` and callback overloads callable. Compose registration once. Apply Configure delegates in registration order, then PostConfigure. Later scalar assignments win, mapping lists append, and header names accumulate. Validate final options at startup. Reject the full DevKit `AddExceptionHandler(...)` chain and the combined setup in either order, naming both in the error. Individual native `AddExceptionHandler<THandler>()` registrations still run in native order.
- **REQ-011** Log handled server exceptions once by default through `ILogger`, accounting for native .NET 10 diagnostics suppression. Preserve standalone handlers and request profiling. When opted in, log a mapped 5xx Result once at execution with the selected status, error types, and available correlation ID. Existing explicit mapper logging takes precedence. Keep Result-only registrations and existing `UseResultLogger()` independent of this policy.
- **REQ-012** Keep `ProducesResultProblem(statusCode)` and `ResultProblemDetailsSchemaTransformer`. Declare statuses explicitly with `application/problem+json`. Document `data`, `data.errors`, `data.result`, `traceId`, `correlationId`, and recursive exception diagnostics with the wire types and optionality. Permit other extension properties. Keep native MVC's top-level `errors` schema. When an MVC endpoint documents both shapes at one status and media type, use schema alternatives.
- **REQ-013** Use the existing server `Presentation.TestHost` with DevKit host configuration, logging, JSON, and request correlation. Keep its AppState and Blazor probes accessible with the Problem Details scenario disabled. Run API and mixed-host checks with fictional in-memory data. Keep WebAssembly test-host startup outside the change.
- **REQ-014** After the HTTP and OpenAPI gates pass, migrate every Hellang consumer, remove the package and exposed helper, regenerate affected lock files and committed API contracts, and document the compatibility changes and new setup.
- **SEC-001** Disclose `exceptionDetails` only when allowed and an opt-in writer path prepares diagnostics. Its entries have string `type` and `message`, optional string `stackTrace`, and optional recursively shaped `innerExceptions`. Use fully qualified CLR types. A diagnostic-only Result error contributes its fully qualified error type and existing diagnostic message. Preserve error and aggregate order. Never emit exception messages or stacks through built-in public `detail` or `data.result`. Keep logs and fixtures free of secrets and sensitive personal data.
- **CON-001** Add no replacement runtime package or duplicate exception and status-page middleware. Keep HTTP-independent Results, application/domain features, the standalone exception chain, authentication policies, serializers, and existing public Result mapping entry points within their current ownership.
- **GUD-001** Follow `AGENTS.md` and `.editorconfig`. Add XML documentation and examples for new public C# APIs. Use fictional models and routes in feature guides and release documentation. Use the repository's centrally managed test tooling.

## 3. Alternatives

- **ALT-001** Keep Hellang. This retains existing behavior but leaves the dependency and incompatible exception/Result shapes.
- **ALT-002** Keep separate legacy payloads while changing the middleware. This avoids some wire changes at the cost of retaining two public contracts and an additional compatibility path.
- **ALT-003** Use framework-default payloads everywhere. This removes existing DevKit Result fields, type URIs, and exception mapping defaults that clients use.

## 7. Risks & Assumptions

- **RISK-001** The native exception middleware clears response headers and offers registered handlers before dispatching to its HTML error page. Lose neither the pre-clear allowlisted headers nor the host's original scope. Verify both in the early fixture, then check the real consuming hosts before the dependency is removed.
- **RISK-002** Framework writers and MVC factories invoke customization at different points. A shared wrapper can double-execute callbacks or mutate fallback payloads if it uses a request-wide flag. Prove behavior with individual writer contexts, body serialization, and counts in TEST-006.
- **RISK-003** The current OpenAPI model advertises an array for `data.errors`. Correct the generated schema and use TEST-010 to catch schema reuse, recursion, or optionality issues. Review regenerated client types before release.
- **ASSUMPTION-001** DoFiesta currently enables Hellang exception disclosure in every environment and does not enable it for Result responses. The migration plan uses Development-only disclosure for both paths, consistent with WeatherFiesta and the combined option. Record the behavior change in release notes.
- **ASSUMPTION-002** Both consuming servers keep their current handler coverage and native HTML fallback. The mixed fixture demonstrates deliberate API-only scope for hosts that choose it.
